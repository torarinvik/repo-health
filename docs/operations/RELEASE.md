# Release and recovery (M12)

## What a release packet contains

Generated by `tools/release-packet.sh` (never hand-written):

- `packet_version` (`rh-release-packet/1`) and a release label;
- the catalog state: implemented count vs the 360 target and the metric keys
  with their versions;
- milestone stages read from `STATUS.md`;
- the reviewed source register (capabilities, unauthorized/unsupported,
  rights, retention);
- the F001–F040 fixture coverage summary;
- the performance manifest location and the note that timings are
  machine-specific;
- security scope and known limitations.

The packet **does not assert test results**; the suite output is attached
separately by running `tools/check.sh`. `tests/test_release_packet.sh`
asserts determinism, schema, and the absence of safety/trust verdicts.

## Signing a release packet (M07-04)

Signing is optional and key-driven. The key is a raw byte file held
separately from workers and is never read from the repository:

```sh
RH_SIGNING_KEY_FILE=/secure/path/release.rhkey \
  bash tools/release-packet.sh build 1.0.0
# -> build/release-packet.sig
./build/rh_cli verify --key /secure/path/release.rhkey \
  --subject build/release-packet.json --sig build/release-packet.sig
```

`rh_cli sign` computes `{"algorithm":"hmac-sha256","subject_sha256":...,
"signature":...}` over the packet bytes. `verify` exits `0` on a match, `5`
on a mismatch, and `3` for unsupported/malformed input. The primitive is
SHA-256 (FIPS 180-4) + HMAC-SHA256 (RFC 2104), checked against published
vectors in `tests/test_m07_sha.sh`.

**What a verified signature means:** the subject bytes are unchanged and
the verifier holds the same shared key. It is *not* a public-key signature,
so a third party cannot verify without the key; and it is **not** a claim
about the correctness, safety, or trustworthiness of the packet, code, or
project (S011).
Keep keys out of the tree (`.gitignore` excludes `*.rhkey` and `ops/keys/`).

## Release checklist

1. `bash tools/check.sh` — all local harnesses pass, exit 0.
2. `bash tools/release-packet.sh <out> <label>` — packet regenerates
   deterministically for the label.
3. Rights: `ops/source-review-register.json` is current for every enabled
   source (`tests/test_m02.sh` / `tests/test_m08.sh` validate it).
4. Restore exercised: `test_m07` backup/restore drill passes.
5. Coverage honesty: `tests/test_profile.sh` and `tests/test_fixtures.sh`
   pass, so no unavailable metric or unbacked fixture is claimed.
6. Attach the suite output and the packet to the release record.
7. If the release is published, sign the packet with a key held outside the
   tree and attach `release-packet.sig`; record the algorithm and that
   verification means integrity + key possession, not safety (M07-04).

## Recovery

- **Corrupt evidence:** stop derived publication, verify digests, compare
  against the backup manifest, restore verified objects only, rebuild, and
  mark affected reports `not_replayable` (runbook 3; `test_m07`).
- **Bad merge:** revoke the link, recompute clusters under a new revision,
  supersede affected derived results (runbook 2).
- **Credential exposure:** revoke first, stop jobs, inspect payloads,
  rotate, add a regression test before restoring (runbook 4).
- **Provider change/outage:** back off, preserve the cursor, mark only the
  affected capability stale/partial, add a sanitized fixture, reconcile
  before declaring restored (runbook 1).

## Never in a release

- A roadmap item presented as released capability.
- A hidden incompleteness score, or any universal health/trust verdict.
- A safety claim derived from a digest, a test pass, or popularity.
